# Phase 0.5b: Budget Writes Through the Outbox (Design)

**Date:** 2026-10-01
**Roadmap:** `docs/plans/2026-09-30-guardrails-roadmap.md` (Phase 0.5)
**Branch:** `phase-0.5b-budget-outbox`

## Goal

`useCreateBudget`, `useUpdateBudget`, `useDeleteBudget`, and `useCopyBudgets` write through the offline outbox. After this phase `src/lib/supabaseQueries.ts` has no direct Supabase writes, and Phase 1's Supabase-write lint rule can land as `error` (with the device-registry allowlist).

## Background (verified 2026-10-01)

- Budgets have no realtime or catch-up path (`SyncTableName` in `src/lib/realtime-sync.ts:75` is transactions, accounts, categories). The only local copy is the per-month mirror written on each online Budgets read (`mirrorBudgetsForMonth`, called from `fetchBudgetGroupsFromServer`), which replaces the month's rows.
- `UNIQUE(household_id, category_id, month)`; `month_key` is a generated column. `LocalBudget` (`src/lib/dexie/db.ts:105`) already omits `month_key`, and Dexie has a `[month+category_id]` index.
- Nothing references `budgets.id` (no foreign keys). The processor already maps `budget` to `budgets`.
- `syncCreate` treats only primary-key duplicates as success (`processor.ts`), so a create colliding on category and month fails terminally today.
- Online, the Budgets page renders the server result; offline it renders `getLocalBudgetGroups` from the mirror.

## 1. Processor: budget creates are upserts

In `SyncProcessor.syncCreate`, budget creates use `.upsert(payload, { onConflict: "household_id,category_id,month" })`; every other entity keeps `.insert`. The payload carries the client `id`, so on conflict the server row takes this device's id and amount (last write wins). An update or delete queued elsewhere against the previous id matches zero rows and is a silent no-op; that device's copy is corrected on its next mirror. `["budgets"]` joins the processor's post-drain invalidation list.

## 2. Mirror keeps pending local work

`mirrorBudgetsForMonth(monthKey, rows)` stays one Dexie transaction (now also over `syncQueue`). Budget queue items with status `queued` or `syncing`:

- Local rows of that month with a pending create or update are kept as they are and win over any server row with the same id or the same category.
- Server rows with a pending delete are dropped.

All other server rows replace the month as before.

## 3. Offline budget mutations (`src/lib/offline/budgets.ts`)

- `createOfflineBudget({ categoryId, month, amountCents }, userId)`: validates the amount; if the month already has a local row for the category (via `[month+category_id]`), returns `updateOfflineBudget(existing.id, amountCents, userId)`; otherwise creates a row with a client UUID and queues a create whose payload omits `created_at` (so a conflict upsert never rewrites the original creation time).
- `updateOfflineBudget(id, amountCents, userId)`: updates the local row; queues `{ amount_cents, updated_at }` only.
- `deleteOfflineBudget(id, userId)`: deletes the local row; queues `{ id }`.
- `copyOfflineBudgets(fromMonth, toMonth, userId)`: source rows from the local mirror when `fromMonth` was mirrored, otherwise a Supabase read; `"No budgets found for previous month"` when empty; per source row, update the target month's existing local row or create a new one; all rows and queue items in one Dexie transaction. Returns the rows written.

All return `OfflineOperationResult` and never throw. No fetch on miss: the Budgets page only shows mirrored rows.

## 4. Hooks

The four hooks keep their call shapes (`{ categoryId, month, amountCents }`, `{ id, amountCents }`, `budgetId`, `{ fromMonth, toMonth }` resolving to a count), use `requireUserId`, throw on `success: false`, and call `afterOutboxWrite(queryClient, userId, [["budgets"]])`. `src/routes/budgets/index.tsx` is unchanged.

## 5. Testing and done criteria

- Processor: budget create sends `upsert` with the conflict target; transaction create still sends `insert`; `["budgets"]` invalidated after a drain.
- Mirror: pending create/update rows survive a re-mirror (including against a server row for the same category); pending deletes are not resurrected; untouched rows still replace.
- Offline functions: row and queue item written atomically; create on an existing category/month queues an update instead; update queues only changed fields; copy from a mirrored month and from the server; empty source returns the error.
- Hooks: never call `supabase.from(...).insert/update/upsert/delete`.
- `grep -nE "\.(insert|update|upsert|delete)\(" src/lib/supabaseQueries.ts` prints nothing; `npm run lint`, `npx vitest run`, `npm run build` exit 0; `npm run test:e2e:smoke` passes on chromium (the budgets spec polls the saved row).

## Decisions & Deferrals

- **Budget creates upsert on category and month, taking over the server row's id (decided 2026-10-01).** Why: the category/month is the budget's real identity; no table references `budgets.id`, so the id can change hands, and it avoids reintroducing id remapping. Cost: another device's later update/delete against the old id is a silent no-op until its mirror refreshes. Revisit: if budgets become concurrently edited across devices.
- **Create on an existing local category/month becomes an update.** Why: avoids a pointless server conflict when the device already holds the row. Revisit: never.
- **The mirror keeps pending local budget work.** Why: replacing the month would hide unsynced changes until the drain lands. Revisit: if budgets join realtime.
- **Create payload omits `created_at`.** Why: a conflict upsert would otherwise overwrite the original row's creation time. Revisit: never.
- **Final review (2026-10-01): upsert verified against real Postgres.** As the `authenticated` role in a rolled-back transaction, the budgets FOR ALL policy allowed ON CONFLICT DO UPDATE including the id change; `created_at` was preserved; a repeated upsert stayed one row. Not verified through PostgREST over HTTP.
- **Deferred: read/drain race on online writes.** `afterOutboxWrite` refetches while the drain runs; if the server read returns before the upsert commits but mirrors after the queue item completes, the month mirror briefly drops a just-created budget or restores a just-deleted one. The drain's own invalidation repairs it online; only going offline inside that window leaves a wrong mirror until the next online read. Revisit: when budgets join realtime, or by capturing pending ids before the server read.
- **Deferred: online page shows server rows only.** A new or edited budget appears once the drain lands (same as 0.5a's server reads). Revisit: if users report the brief stale amount; overlay pending local rows on the online result.
- **Accepted: create on an already-budgeted category overwrites its amount** (previously a unique-violation error). Consistent with the upsert decision and the old copy behaviour. Revisit: if users want a warning.
- **Deferred: offline Add/Copy in a never-mirrored month** succeed locally but show nothing until reconnect; offline copy from an unmirrored source shows the raw fetch error. Revisit: UI pass (disable both buttons in the offline-empty state).
- **Deferred: stale local row whose server row was deleted elsewhere.** An edit (or create-turned-update) against it updates zero rows server-side and the amount is lost at the next mirror. Revisit: when budgets join realtime/catch-up, or make budget `syncUpdate` fall back to upserting the local row when zero rows match.
- **Copy reads the mirror first, even online.** Why: the mirror includes unsynced local edits; it refreshes on every online Budgets read. Revisit: if copies from a stale mirror are reported.
